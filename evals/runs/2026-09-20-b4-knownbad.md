# B4, known-bad half — the release gate at the tagged commit

**Date:** 2026-09-20 · **Benchmark:** [B4](../benchmarks/README.md)
· **Commit under test:** `9a711147ae32a431f007fdc4dbab0d85c29d8737` on `main`
· **Artifacts:** [`2026-09-20-b4-knownbad-artifacts/`](2026-09-20-b4-knownbad-artifacts/)
— 12 known-bad judge cells, 2 positive-control cells, `summary.json`.
· **Runner:** [`evals/harness/run-knownbad.py`](../harness/run-knownbad.py)

## The question

Not "is the toolkit good." This asks whether **the judge in this repo can still say no.**

Every green run in `evals/runs/` is host-judged. The first nine runs in this repo's history were
all-PASS, which is indistinguishable from a judge that never fails anything. The six fixtures in
`evals/known-bad/` exist to make that falsifiable: each pairs a case input with a deliberately
wrong output, and every one must be graded FAIL. If any scores PASS or WEAK, no green run here
means anything.

## Method

Each fixture is stripped of every trace of its own answer before a judge sees it — the
`expect: FAIL` frontmatter, the `plants:` line naming the planted defect, the heading that reads
"Bad output (must FAIL)", and the closing "Why it must FAIL" section that explains the defect in
full. The judge receives the rubric, the case input, and the output. Nothing else.

The strip is asserted, not assumed: the runner raises if any of `must FAIL`, `Why it must FAIL`,
`expect:` or `plants:` survives into what it is about to send. Run
`python evals/harness/run-knownbad.py --show KB4` to read the exact bytes a judge receives and
audit the blinding yourself.

Each judge is a fresh OS process (`claude -p --no-session-persistence`) with no channel to the
authoring conversation. **k = 2**, judge model pinned to `claude-sonnet-5` — Sonnet because
against a two-Opus consensus over 69 cells it scored Cohen's κ 0.68 while Haiku scored 0.51 with
a bias that flipped direction depending on the specialist.

## The positive control, and why 6-of-6 is not enough on its own

Six known-bad fixtures all scoring FAIL is also exactly what a judge with a FAIL bias produces.
The set proves the judge *can* say no; by itself it says nothing about whether it can still say
yes, and a judge that only says no is as useless as one that only says yes.

So one known-**good** output went through the identical path — same rubric, same prompt scaffold,
same model, same blinding. The output is a real verifier run from the 2026-09-20 cross-model
study's guildproof arm (`claude-opus-B1`), on the same route as KB4, scored 6 of 6 there by two
blinded judges.

**Positive control: WEAK / WEAK.** No ❌ from either judge. The judge distinguishes a wrong
output from an imperfect one, so the 6-of-6 above is a property of the fixtures and not of a
judge stuck on one answer.

Two things in *why* it was WEAK rather than PASS are worth recording, because both are real:

1. **The cross-model cell itself carries SessionStart hook noise.** Judge 2 quoted an
   off-contract tail in `claude-opus-B1` — "One housekeeping item from the session hook… What
   project are we working on?" — and marked contract conformance ⚠️ for it. The cross-model run
   doc already lists this leak as a method limit, but this is the first evidence that it is not
   purely cosmetic: an independent judge docked a cell for it. The leak is identical across arms,
   so it does not change that study's comparison, and it does make its absolute scores slightly
   pessimistic.
2. **This runner does not give the judge the agent's own Output contract.** Both judges marked
   section-for-section conformance ⚠️ because they could not see `agents/verifier.md`, and the
   rubric tells a judge to default to weak when uncertain. That caps what the positive control
   can score at WEAK. It is recorded rather than fixed, because changing the instrument after
   seeing a result in order to get a better result is how measurement stops meaning anything.
   Supplying the contract would raise the positive control's ceiling and could not lower any KB
   verdict, since all six were driven by ❌ marks on substance.

## Method limits

- **This is the known-bad half of B4 only.** B4 as specified is every case in `evals/cases/`
  *plus* the six fixtures. **The 38 numbered cases were not re-run at this commit.** The most
  recent full-suite blind run of the numbered cases is 2026-07-21 (36 PASS / 1 WEAK / 0 FAIL),
  which predates the rename and predates case 41. So the claim earned here is narrow and exact:
  the judge can still fail a bad output at the commit being tagged. It is not "the suite is
  green at the commit being tagged."
- **k = 2, one judge model, same family as three of the twelve models in the study it
  calibrates.** A non-Claude judge would be a stronger design and is not yet calibrated.
- **The fixtures were authored by the same person who wrote the rubric they are graded against.**
  A fixture set can be unintentionally tuned to the gates it is meant to test. The mitigation is
  that each fixture plants a defect class found in real output, not one invented to fail.
- **Six fixtures is a floor, not coverage.** They cover faithfulness, injection, SQL injection, a
  laundered blocking verdict, statutory-language stripping, and boilerplate prohibitions. A
  failure class nobody has thought of is not in here. When a red-team finds one, it gets a
  fixture.

## Reproducing this

```bash
python evals/harness/run-knownbad.py --check        # fixture shapes + machine readiness, spends nothing
python evals/harness/run-knownbad.py --show KB4      # the exact blinded judge prompt, spends nothing
python evals/harness/run-knownbad.py                 # all 6 fixtures, k=2
python evals/harness/run-knownbad.py --positive      # the known-good control
```

Cells already on disk are reused rather than re-spent, so a run can be taken in short batches.
The runner exits non-zero unless all six fixtures fail, which makes it usable as a release gate
rather than something a human has to read and interpret.
