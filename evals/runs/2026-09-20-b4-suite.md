## The question

Every case in `evals/cases/` run at the commit being tagged, each one produced and judged in
separate OS processes. `evals/runner.md` describes this protocol for a person driving Claude Code
by hand. That works, and it is also why the last full-suite run in this directory is dated
2026-07-21: it takes an evening, so it does not happen at a tag. `run-suite.py` does the same
thing unattended.

## Read that distribution as a gate, never as a rate

This is the most important thing in the document, and it is a limitation rather than a result.

**First, there is no control arm.** This is a single-arm absolute score. Nothing in the run
measures the same inputs without guildproof, so there is no way to separate what the prompts did
from how harsh this judge is on this day. The benchmarks in `evals/benchmarks/README.md` are
paired for exactly that reason; B4 is not.

**Second, PASS requires a clean sheet.** The verdict rule in `evals/rubric.md` is PASS only with
no ❌ **and no ⚠️**, and the judge stance in the same file is "Default to ⚠️ or ❌ when uncertain."
Counted mechanically across the 34 transcripts, a case carries between 10 and 23 scored bullet
lines (`grep -cE '^[[:space:]]*[-*].*(✅|⚠️|❌|n/a)'` per judge file). A single hedge anywhere in
20 marks costs the PASS. WEAK is therefore the expected verdict for competent output, and 24 WEAKs
is not 24 near misses.

**The corollary runs the other way too.** This directory's 2026-07-21 run reports
**36 PASS · 1 WEAK · 0 FAIL** across 37 cases, and the run before it (2026-06-25) reports
26 PASS · 1 WEAK · 0 FAIL. Neither is credible as a quality measurement either. The 07-21 doc
records its own methodology defect in its third section: wave-1 producers were told to read only
the `## Input` section, `Read` returns the whole file, and so they received the Must and Must-not
lists they were about to be graded against. Two of nine disclosed it unprompted. Its producers and
judges were subagents inside one host session rather than separate processes with no channel
between them. A 36-of-37 PASS rate and a 2-of-34 PASS rate are the same instrument problem seen
from opposite ends.

Use the distribution the way a test suite is used: as a thing that must not get worse between
tags, on a ruler held fixed. Do not publish it as a percentage.

## Five transport bugs

Getting to a trustworthy number took fixing five defects in the harness. Every one produced
plausible output rather than an error, every one would have published a false claim about the
product, and every one was caught by reading a judge's reasoning on a failure instead of accepting
the verdict.

**1. The plugin root does not exist under `claude -p`.** The engine resolves its lens library and
output templates from `${CLAUDE_PLUGIN_ROOT}` at run time
(`skills/prompt-engineering/SKILL.md:155,184`). Under `claude -p` there is no plugin root, so the
model correctly reported that it could not load any lens. The first run scored cases 01 through 04
FAIL, one stated reason being "the output disclaims loading any lenses." Four straight FAILs on
the most central routes. **Would have published:** that `/sharpen` and `/forge-agent` cannot load
their own lenses. A real user installing the plugin has those files. Fixed by inlining the install
directory into the system prompt, labelled as the files it is (`build_system_bundle`).

**2. The agent gallery was not bundled for `forge`.** `/forge-agent` is contracted to seed a new
prompt from a close gallery match. With `agents/` absent, case 03's output said *"I could see only
their one-line descriptions here, not their bodies, so I didn't adapt from them"* and failed the
case's first must item. **Would have published:** that `/forge-agent` builds cold and ignores the
gallery. Case 03 went FAIL to WEAK once the gallery was supplied. Note the fix is scoped: only
`forge` gets the gallery, because pasting twenty agent bodies into a `/sharpen` run would be less
faithful to an install than omitting them, not more.

**3. The command file, which carries the output contract, was not bundled.** For a command route
the contract lives in the command file, not the engine.
`skills/prompt-engineering/SKILL.md:190` says so outright: *"LENS → findings list (no template;
see /lens command)"*. The per-lens block layout, the ✅/⚠️/❌ prefixes, the worst-first ordering,
the top-3-fixes list and the closing `/guildproof:sharpen` offer are all in `commands/lens.md:80-98`
and nowhere else. The producer got the method and was graded against the contract. Cases 05 and 06
failed on exactly the four items only the command file defines. **Would have published:** "the
`/lens` route does not follow its own output contract," at a release tag. Twelve cells are kept in
`quarantine/` with `WHY-QUARANTINED.md`, not deleted, so the defect stays reproducible. They are
not results and must not be counted anywhere.

**4. A producer put its answer inside a tool call and left an apology in stdout.** Case 06's
producer called `ReportFindings` with an empty list, put its actual review inside that call, and
left stdout holding *"The review above is the real output... Please ignore the empty call"*
(`pre-rubric-fix/case-06-output-toolartifact.md`, 342 bytes). A judge then scored the apology and
failed four items, every one of them "there is no review here." **Would have published:** that
`/lens` ignores its contract and returns nothing. Restricting tools by flag does not fix it:
`--allowed-tools ""` leaves Bash, Write, Edit and ReportFindings live, and a deny list blows the
context limit on this machine's MCP surface. So the guard is on the output instead, which does not
depend on any flag's semantics: `TOOL_ARTIFACT` plus a 200-character floor, retry once, then leave
the cell **UNSCORED**. An unscored cell is unmeasured, not passing.

**5. A case Input pointed at a fixture instead of inlining it.** Case 41's input says to send the
block in `evals/benchmarks/fixtures/...`, verbatim. Sending that sentence handed the model a path it
could not read. The verifier replied *"NO VERDICT ISSUED. The artifact was not in the message"* and
was scored as four contract failures and five must-list misses
(`pre-rubric-fix/case-41-judge.md`). **Would have published:** that the verifier cannot produce a
tri-state verdict on its own flagship challenge case. That refusal was the correct behavior under a
broken harness. Fixed by resolving the reference and inlining the file, and by raising rather than
skipping when the referenced file is missing.

The runner carries three further transport defenses inherited from earlier runs, recorded in
`run_claude`'s docstring rather than found here: the prompt goes on stdin because Windows `claude`
resolves to a `.CMD` shim and `cmd.exe` re-parsed arguments containing SQL and backticks;
encoding is explicit because one em-dash in model output crashed the reader thread under the
Windows ANSI codepage and surfaced as an `AttributeError` nowhere near the cause; and
`ANTHROPIC_API_KEY` is popped from the environment because it shadows the subscription login even
with no credits.

## Four defects in the ruler

All four have one shape: **`evals/rubric.md` contradicted the shipped contract, and the judge was
right about the rubric.** Three are now stated in the rubric with dated parentheticals explaining
why; the fourth was fixed in the contract.

**1. Bracketed gap flags scored as unfilled template slots.** The invariant read "No unfilled
`<...>` placeholders remain." A blinded judge failed case 01 three times over `[stack?]`, saying
so in its own words: *"The rubric's literal wording is `<...>`, but square brackets are the same
defect."* They are not.
`${CLAUDE_PLUGIN_ROOT}/templates/sharpened-prompt.md` uses angle brackets for slots the engine
fills, so an unfilled `<...>` means the raw template was handed back.
`skills/prompt-engineering/SKILL.md:106` **requires** a square-bracket flag for any missing fact
and calls inventing one instead "the single failure that makes the draft unusable and
untrustworthy." **Fixing the engine here would have deleted its central behavior to satisfy a
scoring error.** Case 01 FAIL to WEAK (`pre-rubric-fix/case-01-judge.md` versus
`case-01-judge.md`).

**2. No mark existed for not-applicable, so the no-padding rule was unsatisfiable.**
`commands/lens.md` gave three marks, and the no-padding rule says ✅ lines exist only to show what
was checked. An item the artifact never exercises did not pass, so the engine reached for the
nearest mark it had and marked it ✅. Cases 05 and 06 were failed for it:
*"'✅ Preserve voice: not applicable' is not a pass. It is an n/a wearing a ✅."* The fix is a
missing mark in the contract, not a correction to a disobedient model: `commands/lens.md` now
carries a `—` mark for inapplicable items and says why in its own dated note. **See the sixth
transport defect below: this fix never reached a producer in this run.**

**3. The `/guildproof:sharpen` offer was required on the `--fix` path.** `commands/lens.md` Step 5
requires the offer on the critique path and only there, then sends `--fix` straight to Step 6. The
rubric did not make the split, and cases 31, 32 and 33 were failed for omitting an offer the
command file tells them not to emit. One judge named the cause exactly: *"The rubric gives no
`--fix` exemption for this invariant."* It was right about the rubric.

**4. A one-line summary was required last on the `--fix` path.** The contract asks for the
corrected artifact, then a summary in which **every change names the finding it answers**, then to
**close with any unfixed observations**. A per-change table is the correct form of that summary,
because the table is the minimality check made visible, and the last section is the unfixed list.
The rubric implied a one-line summary in final position. Case 32's second judging failed on
exactly this: *"The summary is a multi-row table..., not one line. The output then goes on to...
'Unfixed observations and open questions', so it doesn't end on any summary."*

Four ruler defects against zero confirmed engine defects on those cases is a finding about this
repo's measurement hygiene, and it is the run's most transferable result. The judge was doing its
job correctly in every instance. It failed outputs for disobeying a rule the product had never
been given.

## Two more defects, found while writing this document

Both cut against the run. They are here rather than in a follow-up because a run document that
omits what its own author found while reading the artifacts is not evidence.

### A sixth transport defect: the bundle cache is never invalidated

`build_system_bundle` caches one system bundle per route signature and returns early when the file
already exists (`run-suite.py:249-251`). Nothing compares the cache against the files it was built
from. Exactly one bundled input changed mid-run: `commands/lens.md`, edited to add the `—` mark
described above. The cached lens bundle was never rebuilt.

Clone-verifiable: `_bundles/bundle-SKILL-lens.md` has one commit in its history, `4572116`, which
precedes the `commands/lens.md` edit in `34ee891`, and the new rule's text does not appear in it.

```bash
grep -c "does not apply to this artifact" commands/lens.md                                   # 1
grep -c "does not apply to this artifact" evals/runs/2026-09-20-b4-suite-artifacts/_bundles/bundle-SKILL-lens.md   # 0
git log --oneline -- evals/runs/2026-09-20-b4-suite-artifacts/_bundles/bundle-SKILL-lens.md  # 4572116 only
```

Local mtimes corroborate: the bundle was written at 13:09:26, `commands/lens.md` was edited at
16:25:56, and the eleven producer cells that use that bundle and were produced after it are cases
05 (16:30), 06 (16:36), 23 (16:48), 29 (17:07), 30 (17:10), 31 (17:14), 32 (17:18), 33 (17:19),
35 (17:30), 36 (17:33) and 37 (17:36). Grade routes are included because `ROUTE_COMMANDS` maps
both `lens` and `grade` to `commands/lens.md`, so they share one bundle signature.

Three consequences, all of which weaken the run:

- **The `—` mark fix is unmeasured.** No producer in this run received it. Case 06 improvised `n/a`
  instead (`case-06-output.md:27`), which its judge noted and let pass while observing that "the
  LENS invariant lists only three marks." Case 05 used no not-applicable mark at all and was marked
  ⚠️ on no-padding again for ✅ lines that are "non-checks," which is the same defect the fix was
  written to close.
- **The `05 FAIL to WEAK` delta recorded in `34ee891` cannot be attributed to that fix.** Case 05
  was re-produced and re-judged, so the delta mixes a new producer sample, a new judge sample, and a
  contract change that was never delivered. Case 01's delta is clean by contrast, because the
  bracket distinction lives in `rubric.md` and reaches the judge directly.
- **Eleven of the 34 judged cells were produced against a version of `commands/lens.md` that is not
  the one at the commit under test.** The differences are confined to the not-applicable mark, so
  this is narrow, and "the suite ran at one commit" is still not strictly true.

The fix is to hash the bundled inputs into the cache key, or to clear `_bundles/` whenever a
bundled input changes. Neither is done.

### Case 30's FAIL rests on a case-list item the shipped contract forbids

This is a fifth defect of the same class as the four above, and it sits in a case file rather than
in the rubric.

Case 30's input is `/guildproof:lens --lens ai-tells` with no `--fix`
(`evals/cases/30-lens-ai-tells.md:12`). Its must list ends with *"Produce the cleaned rewrite, then
run the **second pass** and report it."* The judge failed the case on that item and nothing else:
*"No cleaned rewrite exists anywhere in the output."*

The lens file forbids the rewrite. `lenses/ai-tells.md` states, under a heading that says the lens
never decides this for itself:

> **LENS without `--fix` (the default):** findings only, each with its proposed replacement quoted
> inline. Run steps 2–3 as *internal* work to validate the replacements you propose. **Do not emit
> a rewritten artifact** — the command's default contract is critique, not rewrite, and a lens may
> not override it.

The output did exactly that: per-span replacements quoted inline, an internal pass over them, no
rewritten artifact, and an explicit pointer that `--fix` would produce one. Its judge even
considered the excuse and half-accepted it: *"The stated reason, that a full rewrite needs invented
facts, may be sound."* The real reason is stronger than the one the output gave, and it is in the
lens file.

Case 30 carries exactly one ❌. **I do not believe this FAIL, and the commit message's claim that
all eight were checked against the shipped contract and are genuine does not hold for this one.**
The fix belongs in the case file, and the case needs re-judging before its verdict is quoted. I
have deliberately not re-scored the distribution above: what is on disk is 8 FAIL, and a run
document that edits its own numbers to match a later finding is worth nothing.

A smaller instance of the same thing sits inside case 36. Its second ❌ is *"A '## Next' section
follows the Skip line, so the output does not end there."* The shipped contract requires that
section: `commands/lens.md` Grade mode says "End with the next step," and
`templates/graded-prompt.md` places `## Next` after the Skip line. Case 35's judge treated the same
shape as a ✅ on a must item. Case 36 still fails on its first ❌, which is genuine, so the verdict
stands and only that one mark should be discarded. Two judges scoring the same structure opposite
ways is worth more attention than either mark.

## The eight FAILs

Each was checked against the shipped contract before being believed, which is how cases 30 and 36
were caught above. The other seven are product findings, and most are modest.

**Case 06, `lens`, dogfooding a review of a weak prompt.** The case's must list names six
weaknesses the review has to flag. Five are covered. The judge: *"**Self-check:** missing. No
finding or fix says the prompt lacks a verify-before-answering step. 'What it does when unsure' is
uncertainty handling, not a self-check, and the top-3 fixes omit it too."* Everything structural is
✅ and the findings are specific and correctly ordered. This is a recall miss on the review's own
checklist, not a format or contract failure, and it survives the transport fixes.

**Case 10, `agent`, `debugger`.** The case asks for three strong candidates behind an
intermittent stale-read bug. Two appear. The judge: *"**Optimistic UI not reconciled with server
response is never named as a hypothesis.** The word 'optimistic' does not appear... H2's 'overwrite
the fresh state' race gets near the mechanism, but the candidate is not surfaced or probed as its
own cause."* Everything else holds, including the self-challenge and the discriminating probes:
*"Without the optimistic-UI omission this would be WEAK."* This was **deliberately not fixed**. It
is a k=1 recall miss against an author-chosen candidate list, the prompt asks for ranked hypotheses
and sets no coverage quota, and patching it to name the missing candidate would tune the prompt to
one eval case. If it reproduces at higher k it becomes a prompt change.

**Case 20, `agent`, `backend-builder`.** The output states a security property its own design does
not have. The judge, on the guardrail hard gate: *"The Contract says 'The **plaintext token
appears only in this response**'. The code comment says 'The token is shown here and never
retrievable again.' Both are false against the output's own design... The token is therefore
re-issued on every replay while the link is live, and the server can regenerate any token from its
HMAC key."* The contradiction is internal to the output, so no missing file explains it, and its
own self-challenge block did not catch it: *"it reads as ticked boxes."* The rest of the code is
strong, with in-query authorization, a race-safe cap and honest unverified-work disclosure. A false
security claim in shipped-looking code is the most consequential of the eight.

**Case 28, `sharpen`, prohibitions coverage.** *"Four of the seven assumptions have one, and
three do not."* The "Override with:" line is in the shipped output template
(`templates/sharpened-prompt.md:42-43`), so the invariant is the product's own. The judge is
explicit that everything else held: *"The output is strong on every case-specific criterion and
would probably score WEAK or PASS on quality alone."* Reversibility of assumptions is the whole
point of labelling them, so three silent ones is a real regression and a narrow one.

**Case 30, `lens`, `ai-tells`.** Not credible as a product finding. See the section above.

**Case 35, `grade`, weak prompt.** Two ❌. The first is genuine and is the product's own rule:
*"**Would steer** quotes nothing from the prompt."* `skills/prompt-engineering/SKILL.md:239`
requires a quote per quality dimension and `templates/graded-prompt.md` repeats it. The second is
a severity mismatch rather than a missing capability: the case expects Output format ❌ and the
output marked it ⚠️ on substantively the same evidence, *"covers length only. There's no shape,
channel, structure, or handoff format."* The judge conceded the mark was arguable, *"length alone
is thin support for a partial mark."* This is the weakest of the seven I do believe.

**Case 36, `grade --against`, regression under an overall win.** *"Several ✅ marks have no quote
at all: Role, Objective, Prohibitions, Out of scope, Bounded and Would steer, for A and B alike.
The output concedes this in its own header."* Same rule as case 35, at larger scale: six of
fourteen marks unsupported. A second finding is worth recording even though it did not drive the
verdict, because the output invented a rule about the rubric it was scored under: the judge flagged
*"an unsupported claim that 'restoring it takes B to 2 ⚠️, which is PASS'... The rubric I was given
has no '≤2 ⚠️' PASS threshold."* The case's core test passed cleanly: the regression is named
beneath the win, and no merged prompt was emitted.

**Case 41, `agent`, `verifier`, the public planted-leak challenge.** The judge read
`agents/verifier.md` and found a named section missing: *"The contract lists these sections:
Verdict, Independence, Observable evidence, **Assessment**, Defects, Claimed vs. actual,
Confirm-these, How each clean axis was checked. The output has no Assessment section."* The
Observable-versus-Assessment split is the mechanism that makes a verifier's output auditable, and
the judge shows it blurring in practice: library semantics are listed as observable evidence while
the output elsewhere admits *"stated from library semantics, not executed here."* The substance was
excellent. Every must and should item was caught, including the `org_id` gap, the named sensitive
fields, the `c.id` collision and the dead `!invoice` branch, and no must-not was violated.
*"The analysis is excellent... The output fails the rubric's structural gate because it drops the
contract's Assessment section."*

## The 24 WEAKs, and what a WEAK is here

A WEAK means the judge found at least one ⚠️ and no ❌. Given the stance and the mark count, this
is where competent output lands. Reading all 24 transcripts, the ⚠️ marks cluster into four
recurring shapes, and all four are real:

1. **Facts leaking in unbracketed.** Cases 02, 08, 12, 13, 16, 21, 26, 27 all hold the faithfulness
   or guardrail dimension at ⚠️ rather than ✅. Case 12's output pulls in specifics the case never
   supplied, naming "BoardPath's document ingestion" and a "Warning Center." Case 13's governance
   letter cites no section or statute, correctly, and then asserts facts it was never given in
   unbracketed text, plus two unsourced legal generalizations. This is the single most common
   finding in the run, and it is the class the repo claims to defend against.
2. **Overlapping or unmapped scales.** Cases 03, 16, 24, 25, 27 hedge on mark discipline. Case 16:
   *"The marks are inconsistent. '❌ **High**: token entropy' and '⚠️ **High**: state-changing
   operation on GET' have the same severity but different marks. The mark never maps cleanly to
   severity."* Case 03's forged contract emits severity and a mark with no stated mapping between
   them.
3. **Padding, or a finding the output itself says to skip.** Cases 05, 29, 31, 33. Case 29 raises
   an 18px padding finding against a grid it inferred, then tells the reader to skip it. Case 31
   flags a phrase and lists the same phrase under carve-outs: *"It can't be both flagged and
   skipped."*
4. **A self-challenge that ran and reported clean anyway.** Cases 12, 13, 15, 16, 26, 34. Case 13:
   *"The check happened and reported a false all-clear."* Case 26: *"the method's step-6 checks...
   visibly missed the co-critical"* path.

Two WEAKs are worth naming individually. Case 14 and case 32 are the PASSes, and case 14 earned it
on the honest-degradation case: the judge checked every cited paper and figure against its own
knowledge and found no invented source, author, figure or quote. Case 09's ⚠️ is a judge declining
to accept a declared omission: *"I'm not scoring it ✅, because large values are named in the must
list and were deferred without a sound reason."* That is the stance working as designed.

## The four orchestration cases are UNMEASURED-BY-TRANSPORT, not passing

Cases 17, 18, 19 and 22 were not run. `/orchestrate` needs a host that can dispatch to registered
subagents. `claude -p` cannot: nothing is registered, so the model would improvise a shape that is
not the product, and a scorecard would then be reporting an improvisation. The runner refuses them
by route and attaches the reason to the cell (`run-suite.py:440-443`). `evals/rubric.md` agrees:
"Until Layer 2 ships, a case on this route scores **N/A — blocked**, not PASS/FAIL."

`--include-orchestration` will run them anyway. The docstring's instruction is to not put the
result in a scorecard.

**These four are not a gap in the product, they are a gap in the measurement, and the measurement
is benchmark B5.** B5 is specified in `evals/benchmarks/README.md` as the one benchmark that cannot
use the cross-model harness, comparing a single-conversation build against the same request through
`/orchestrate`. Until it runs, `/orchestrate` carries four eval cases and one live seven-agent
demonstration, which is a demonstration and not a measurement.

One honest caveat on the exclusion: it is by **route**, not by whether a case needs dispatch. Cases
18 and 22 test the Step 0 gate, which fires before anything is dispatched. Case 18 asks that a
single-domain request must **not** orchestrate and case 22 asks that a harmful multi-domain request
be refused rather than decomposed. Both plausibly measure under this transport. Neither was tried,
and claiming they are unmeasurable is stronger than what has been shown.

## Method limits

- **k = 1 per case**, not the k ≥ 2 the benchmark house rules require. Every verdict here is one
  producer sample scored by one judge sample. Case 32's three judgings of one output are the only
  place in the run where judge variance is visible at all, and case 05's FAIL-to-WEAK move mixes
  producer variance with judge variance and cannot separate them.
- **One producer model and one judge model, both `claude-sonnet-5`.** Same vendor, same family,
  self-judging at the family level. A non-Claude judge would be a stronger design and is not
  calibrated here.
- **The rubric changed mid-run, so cases judged before and after the corrections were not scored by
  an identical ruler.** Cells landed across four commits: `4572116` (cases 01 through 10),
  `6ec7fdc` (11 through 14), `34ee891` (15, 16, 20, plus re-runs of 01, 05, 06) and `1c5d7c6` (21
  through 41). The bracket distinction landed in `34ee891` and the `--fix` split in `1c5d7c6`. Cases
  affected by a correction were re-judged and the superseded cells kept in `pre-rubric-fix/`, but
  the cases that were never re-judged were also never re-checked against the corrected rubric.
- **Eleven cells were produced against a stale cached contract.** See the sixth transport defect.
- **The judge's information set was not uniform, and this is the largest uncontrolled variable in
  the run.** The judge is an agentic `claude -p` with filesystem access. At least nine judge
  transcripts state that they read a shipped contract off disk (cases 09, 10, 15, 24, 25, 27, 29,
  34, 41), and at least five state that they could not see one (cases 05, 07, 08, 14, 20). Case
  20: *"I don't have the agent file's Output contract. I scored against the five sections the case's
  must list names."* Case 27's judge flagged the deviation itself: *"I read
  `agents/compliance-reviewer.md` to check the output contract. The rubric says the judge sees only
  the input, output and rubric, so this read is a deviation from that."* This cuts both ways and
  neither direction is controlled. A contract-blind judge defaults to ⚠️ under the rubric's own
  stance, which depresses the score; a contract-reading judge can fail a section-for-section
  mismatch that a blind judge would never see, which is precisely what happened to case 41. The
  same effect is recorded independently in the known-bad half, where both judges capped the positive
  control at WEAK because they could not see `agents/verifier.md`.
- **Four cases are unmeasured**, and two of those four may be measurable. See the section above.
- **Cases and rubric were authored by the same person who built the prompts they grade.** Mitigated
  only by the known-bad half, which shows the judge can still fail a bad output at this commit.
- **The `/lens` and `/sharpen` routes were graded against a rubric that contradicted their shipped
  contracts in five places.** Four are fixed. The fifth, in case 30, is not.

## Reproducing this

```bash
python evals/harness/run-suite.py --check          # what it would run, and the call count. Spends nothing.
python evals/harness/run-suite.py --show 07        # the exact producer and judge prompts for one case. Spends nothing.
python evals/harness/run-suite.py --tabulate       # rebuild the scorecard from the cells on disk. Spends nothing.
python evals/harness/run-suite.py --only 07,13,21  # specific cases
python evals/harness/run-suite.py --route agent    # one route, in a short batch
python evals/harness/run-suite.py                  # everything runnable
```

`--check`, `--show` and `--tabulate` make no model calls. The other three do.

Cells already on disk are reused rather than re-spent, so a run can be taken in short batches. That
caching is also the re-judging mechanism: delete `case-NN-judge.md` to re-judge the same producer
output, delete `case-NN-output.md` to re-produce. **Delete the matching `_bundles/bundle-*.md` as
well if any bundled input changed**, because nothing else invalidates it.

To reproduce the quarantined defect, or to re-run those cases properly:

```bash
python evals/harness/run-suite.py --only 01,02,03,04,05,06
```

To see what a producer now receives, including the command file that was missing when those cells
were quarantined, run `--show 05`.
