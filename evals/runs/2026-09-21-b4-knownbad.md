# B4, known-bad half — the release gate at the v0.4.0 tag candidate

**Date:** 2026-09-21 · **Benchmark:** [B4](../benchmarks/README.md)
· **Commit under test:** `218563ce584d8e397cc4bc47d6a5d5250936f0cc` on `main`
· **Artifacts:** [`2026-09-21-b4-knownbad-artifacts/`](2026-09-21-b4-knownbad-artifacts/)
— 12 known-bad judge cells, the positive-control cells, and `summary.json`.
· **Runner:** [`evals/harness/run-knownbad.py`](../harness/run-knownbad.py)

This is the re-run that B4's own rule requires at a tag candidate. The
[2026-09-20 run](2026-09-20-b4-knownbad.md) tested `9a71114`; this one tests the merge commit the
v0.4.0 tag will point at, which lands the orchestration halt fix, the run manifest, the third arm,
and the claim rewrite.

## The question

Not "is the toolkit good." This asks whether **the judge in this repo can still say no.**

Every green run in `evals/runs/` is host-judged, and the first nine runs in this repo's history were
all-PASS, which is indistinguishable from a judge that never fails anything. The six fixtures in
`evals/known-bad/` exist to make that falsifiable: each pairs a case input with a deliberately wrong
output, and every one must be graded FAIL. If any scores PASS or WEAK, no green run here means
anything.

## Method

Unchanged from 2026-09-20, deliberately — changing the instrument between a baseline and a re-run
makes the two incomparable.

Each fixture is stripped of every trace of its own answer before a judge sees it: the `expect: FAIL`
frontmatter, the `plants:` line naming the planted defect, the heading reading "Bad output (must
FAIL)", and the closing "Why it must FAIL" section. The judge receives the rubric, the case input,
and the output. Nothing else.

The strip is asserted rather than assumed — the runner raises if any of `must FAIL`,
`Why it must FAIL`, `expect:` or `plants:` survives into what it is about to send. Audit it yourself
without spending anything: `python evals/harness/run-knownbad.py --show KB4`.

Each judge is a fresh OS process (`claude -p --no-session-persistence`) with no channel to the
authoring conversation. **k = 2**, judge model pinned to `claude-sonnet-5`.

**Every cell was generated fresh.** `summary.json` records `"cached": false` on all 12, so this is a
real re-run and not the previous run's artifacts reused under a new date. That mattered enough to
check: the runner reuses cells on disk by design, and a gate that silently replayed a prior verdict
would be worthless at a tag.

## The positive control, and why 6 of 6 is not enough on its own

Six known-bad fixtures all scoring FAIL is also exactly what a judge with a FAIL bias produces. The
set proves the judge *can* say no; by itself it says nothing about whether it can still say yes, and
a judge that only says no is as useless as one that only says yes.

So one known-**good** output went through the identical path — same rubric, same scaffold, same
model, same blinding. The output is a real verifier run from the 2026-09-20 cross-model study's
prompted arm (`claude-opus-B1`), on the same route as KB4.

**Positive control: WEAK.** No FAIL mark. The judge distinguishes a wrong output from an imperfect
one, so the 6 of 6 above is a property of the fixtures rather than of a judge stuck on one answer.

Why it is WEAK rather than PASS is unchanged from 2026-09-20 and both causes are real:

1. **The cross-model cell itself carries SessionStart hook noise**, an off-contract tail that an
   independent judge docked it for. The leak is identical across arms, so it does not change that
   study's comparison, and it does make its absolute scores slightly pessimistic.
2. **This runner does not hand the judge the agent's own Output contract**, and the rubric tells a
   judge to default to weak when uncertain, which caps the control at WEAK. Recorded rather than
   fixed: changing the instrument after seeing a result in order to get a better result is how
   measurement stops meaning anything. Supplying the contract would raise the control's ceiling and
   could not lower any KB verdict, since all six were driven by fail marks on substance.

## Method limits

- **This is the known-bad half of B4 only.** B4 as specified is every case in `evals/cases/` *plus*
  the six fixtures. **The 38 numbered cases were NOT re-run at this commit.** The most recent blind
  run of the numbered half is [2026-09-20 at `1c5d7c6`](2026-09-20-b4-suite.md) — 34 of 38 judged,
  2 PASS / 24 WEAK / 8 FAIL, 4 unmeasured by transport — which is a regression gate and not a rate.
  So the claim earned here is narrow and exact: **the judge can still fail a bad output at the commit
  being tagged.** It is not "the suite is green at the commit being tagged," and the release notes
  must not round it up to that.
- **k = 2, one judge model, same family as three of the twelve models in the study it calibrates.** A
  non-Claude judge would be a stronger design and is not yet calibrated.
- **Six fixtures is a floor, not coverage.** They cover faithfulness, injection, SQL injection, a
  laundered blocking verdict, statutory-language stripping and boilerplate prohibitions. A failure
  class nobody has thought of is not in there. When a red-team finds one, it gets a fixture.
- **The fixtures were authored by the same person who wrote the rubric they are graded against.** The
  mitigation is that each plants a defect class found in real output rather than one invented to fail.

## Reproduce

```bash
python evals/harness/run-knownbad.py --check        # fixture shapes + machine readiness, spends nothing
python evals/harness/run-knownbad.py --show KB4     # the exact blinded judge prompt, spends nothing
python evals/harness/run-knownbad.py --out <dir>    # all 6 fixtures, k=2
python evals/harness/run-knownbad.py --positive --out <dir>
```

The runner exits non-zero unless all six fixtures fail, so it is usable as a gate rather than
something a human has to read and interpret.
